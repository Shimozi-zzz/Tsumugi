# 0001 · 文档切分策略

日期：2026-08-05
状态：已接受（Phase 1）

## 决策

采用"**段落/标题感知的贪心打包 + 句子边界硬切 + 固定 overlap**"策略：

- 预处理：统一换行符（`\r\n`→`\n`），按空行切成"段落"，段落内再按
  Markdown 标题行（`#`~`######`）拆分，让标题独立成块。
- 打包：按段落顺序累加，只要 `当前块 + 下一段 <= chunk_size` 就继续合并，
  否则封存当前块、另起一块。这样能保持段落完整，语义损失最小。
- 超大段落（单段 > chunk_size）：优先在句子边界（`。！？；，…` 等）处切，
  其次空白处，最后硬切，并带 overlap。
- 相邻块 overlap：封存后，下一块用上一块**末尾 chunk_overlap 个字符**作前缀。

## 参数

| 参数 | 默认值 | 理由 |
| --- | --- | --- |
| `chunk_size` | 512 字符 | bge-small 单次编码上限为 512 token；中文按字符计约 512 字符/块，是"语义完整"与"检索精度"的常见折中。 |
| `chunk_overlap` | 64 字符 | 约为 chunk 的 1/8，足以把跨块断开的上下文（尤其中文句意）衔接回来，又不至于引入过多重复。运行时钳制到 `chunk_size//2`。 |

> 小决策：chunk_size 按**字符**而非 token 计，理由：切分逻辑不依赖分词器，
> 实现透明、测试确定性强；代价是英文/代码块可能超过 token 上限，由
> prompt 侧截断兜底（见 0003）。

## 放弃的方案

- **纯固定长度硬切**：实现最简单，但容易从句子中间切断，破坏语义。
- **语义边界切分（embedding 相似度检测边界）**：效果好，但每段都要编码、
  计算成本高，且对短段落文档收益不明显。留作未来优化点（可用 MMR 同期的
  "语义边界"策略一起做）。
- **递归式文本切分器（如 LangChain RecursiveCharacterTextSplitter）**：
  AGENTS.md 要求核心逻辑手写，且该策略本质上也是"分隔符 + 长度"的变体。

## 已知限制

- 未处理 Markdown 表格、代码块（不保证整表/整代码块在一个 chunk 内）。
- 中文按字符切，无词边界感知。
- 图片不做切分与语义检索（Phase 1 明确范围）。
